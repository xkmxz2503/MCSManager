# MCSManager Panel 插件系统计划书

## 1. 复审结论

原方案正确地将首版范围限制在 Panel 与前端，但在实施前必须修正以下问题。

| 优先级 | 问题 | 本次修订后的决策 |
| --- | --- | --- |
| P0 | 在 Panel 进程内执行的 CommonJS 插件无法保证崩溃、死循环、内存泄漏或无法完成的激活不会影响 Panel。 | 首版只保证清单校验、加载异常和释放异常的隔离。插件仍是受信任的同进程代码；进程隔离属于后续不兼容的架构演进。 |
| P0 | 要求插件作者在每个处理器中自行添加 `permission()`，会使鉴权变成可选项。前端描述符过滤无法保护 API。 | 宿主路由门面要求每个端点注册时声明权限等级，并由宿主注入现有的 Panel 权限中间件。 |
| P1 | 原方案没有定义远程浏览器模块如何成为当前前端中的 Vue 路由和布局卡片。 | `PluginOutlet` 是宿主 Vue 组件。插件注册表添加真实的路由记录和可变的卡片注册项；远程模块只实现小型挂载契约。 |
| P1 | 现有布局格式为全局持久化，未知卡片类型会渲染为空白区域。 | 插件卡片采用稳定、带命名空间的类型字符串。`PluginOutlet` 能识别不可用卡片并渲染宿主标准兜底状态，不修改已保存的布局。 |
| P1 | 仅校验路径不足以防护符号链接或替换后仍被缓存的静态文件。 | 宿主拒绝符号链接，使用 `realpath` 校验包含关系，仅挂载 `public/`，并对清单引用入口文件设置不缓存。 |
| P1 | 原前端发现顺序早于 i18n 与用户信息都可用的时机。 | 在核心 i18n 初始化和用户信息获取之后、`createApp()` 之前执行发现。描述符接口由宿主鉴权并按角色过滤。 |

## 2. 目标与范围

构建一个面向受信任管理员的版本化插件宿主。插件只允许贡献：

- 位于自身命名空间下的 Panel HTTP 端点。
- 独立的顶级 Panel 导航页面。
- 可在现有布局编辑器中选择的仪表板卡片。

首版不修改 Daemon、Daemon 协议或 Socket.IO，也不包含上传界面、插件市场、依赖安装、热重载、运行时启停和不受信任代码沙箱。

## 3. 架构

```text
plugins/packages/<plugin-id>/plugin.json
            |
            v
PluginManager（清单校验与生命周期注册表）
   |              |                       |
   |              |                       +-- 激活门面 --> 命名空间 Koa Router
   |              +-- 仅公开静态中间件 --> /plugins/<plugin-id>/
   +-- 已鉴权描述符 API --> 前端 PluginRegistry
                                              |             |
                                              |             +-- 卡片注册表 --> PluginOutlet
                                              +-- Vue 路由 --> PluginOutlet
```

`PluginManager` 放在 `panel/src/app/plugins/`。发现、清单校验、激活、状态记录、静态中间件创建、描述符生成和释放都集中在该高内聚模块中。它可以依赖现有日志器、角色枚举、权限中间件和存储工具。公开插件上下文不得包含 Koa 应用、核心服务或 Daemon 客户端；这只限制受支持的耦合方式，并不是受信任同进程代码的安全边界。

前端注册表放在独立的 `frontend/src/plugins/` 模块中。它获取描述符、加载当前语言资源、通过 Vue Router 注册路由，并沿用现有卡片池路径追加卡片定义。`PluginOutlet` 是宿主 Vue 组件与浏览器加载插件模块之间唯一的桥梁。

## 4. 启动与请求顺序

1. 初始化 Panel 配置以及既有的用户和节点服务。
2. 扫描 `plugins/packages/` 的直接子目录，校验每份清单，并激活有效且启用的服务端入口。激活异常只禁用当前插件，并写入注册表。
3. 在通用协议中间件之后、Panel 根 `public/` 静态中间件之前安装插件静态中间件。每个中间件只能服务于一个插件已校验的 `public/` 根目录。
4. 挂载核心 `/api` 路由，再在同一个 `/api` 路由下挂载宿主描述符路由和每个已激活插件路由。除宿主拥有的挂载点外，`PluginManager` 不直接向应用添加中间件。
5. 所有上述同步启动工作成功后才开始监听。收到 `SIGTERM`、`SIGINT` 或 `SIGQUIT` 时，按激活的逆序释放插件；任意释放失败都记录日志并继续退出流程。

宿主必须记录 `discovered`、`active`、`disabled` 或 `failed` 状态，以及阶段和已净化的错误摘要；不得向普通用户暴露故障细节。

## 5. 安全与信任边界

- 插件安装是管理员控制的操作系统级行为。同进程插件与 Panel 具有相同级别的 Node.js 权限，因此本设计不是沙箱。
- 宿主在激活前校验 ID、路径、贡献项 ID、权限、尺寸、类别和重名项；在挂载静态文件前递归拒绝包内所有符号链接。任何被拒绝的贡献项都会使整个插件被拒绝，不能部分注册。
- 宿主拥有 `/api/plugins`、`/plugins` 和 `/plugins/<plugin-id>`。插件不能选择其他前缀，也不能挂载应用级中间件。
- 宿主路由门面为每个插件端点注册 `permission({ level })`。插件可以选择更严格的等级，但不能绕过令牌、AJAX、会话、限流或角色检查。
- 只有已认证的描述符请求可以获得页面或卡片元数据，宿主会按请求用户的当前角色过滤。这是可用性边界，不能替代端点鉴权。
- 插件包是不可变的部署输入。唯一可写位置是成功激活后创建的 `plugins/data/<plugin-id>/`。插件代码获得该目录的绝对路径，但仍须校验用户控制的文件名。

## 6. 前端集成

核心初始化先获取 Panel 状态、初始化核心 i18n，并加载现有布局配置。之后插件注册表获取用户信息、拉取按角色过滤的描述符、合并插件语言资源，并在 `createApp()` 之前注册贡献项。

每个页面描述符都注册一个稳定名称，例如 `plugin:<plugin-id>:page:<page-id>`，规范路径为 `/plugins/<plugin-id>/<page-id>`，组件为宿主 `PluginOutlet`，并使用含 `mainMenu`、`permission` 的标准 `RouterMetaInfo`。首版插件页面只能是顶级路由，不接受核心路由子项、重定向、图标或自定义路由守卫。

每个卡片描述符都向宿主组件映射和现有卡片池追加一项。其持久化类型为 `plugin:<plugin-id>:card:<card-id>`。`PluginOutlet` 接收完整的持久化 `LayoutCard`，校验类型是否仍激活且当前角色是否有权访问，再加载和调用模块。缺失、禁用、失败或无权访问的卡片显示宿主标准不可用状态。移除插件时不重写现有布局。

## 7. 实施阶段

1. 增加宿主类型、纯清单和路径校验及单元测试。在加载可执行代码前确定完整错误模型。
2. 实现 `PluginManager` 发现、生命周期注册表、路由门面、静态中间件、描述符路由和优雅释放。为重名、路径、链接、激活失败和权限注入增加测试。
3. 实现前端描述符服务、注册表、`PluginOutlet`、i18n 资源合并、动态路由注册、卡片池注册和不可用卡片兜底。
4. 提供一个已打包的示例插件，包含一个管理员 API、一个菜单页面和一个卡片。人工演练完整的启动、登录、刷新、移除和恢复流程。
5. 执行聚焦的 Panel 构建、前端类型检查和相关测试，并在变更记录中说明实际执行的验证。

## 8. 验收条件

- 没有 `plugins/` 目录时，Panel 与前端行为完全不变。
- 重启后有效示例包会激活；管理员可使用其页面、卡片、静态模块和受保护 API。
- 低角色用户既不会获得受限描述符，也无法访问受限插件 API。
- 非法清单、重复 ID、符号链接、越界路径、客户端加载失败、激活抛错和释放抛错均被隔离，并以插件身份记录日志。
- 只能服务于插件包 `public/` 下的文件；替换包后不会继续执行陈旧客户端入口。
- 移除插件后，匹配的布局项仍被持久化并显示宿主不可用状态；恢复相同插件 ID 和卡片 ID 后可再次渲染。
- 文档不再对同进程受信任插件作出进程级隔离承诺。
